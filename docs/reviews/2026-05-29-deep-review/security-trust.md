## Detailed Notes

Authentication is split as intended: docs describe session auth for backoffice/web and JWT bearer for admin API (`docs/INDEX.md:18`), while `Authentication#find_authenticated_user` accepts bearer token first and session fallback second (`app/controllers/concerns/authentication.rb:23`). This is workable for MVP, but it means any controller that includes `Authentication` can accept either credential type unless explicitly constrained. The current admin base relies on the same concern (`app/controllers/admin/base_controller.rb:3`), so admin API is not JWT-only in code even though the docs call it a JWT surface.

The ad-hoc grant model follows the accepted deny-overrides-role design in spirit: latest active grant returns `grant.allow` before role permissions are checked (`app/services/authorization_service.rb:8`). Grant creation requires a reason and creates an audit event (`app/controllers/backoffice/grants_controller.rb:17`). However, there is no expiry UI/use in the controller, no second approval for high-risk grants, and no protection against an admin granting themselves sensitive powers. Because permission mappings themselves are mutable through backoffice (`app/controllers/backoffice/permissions_controller.rb:11`), role-permission edits should be treated as security-admin actions with stronger audit metadata and possibly second approval.

Admin/backoffice separation is mostly namespace/UI separation, not a strict trust boundary. `Backoffice::BaseController` and `Admin::BaseController` both authenticate with the same concern and both start with `backoffice.access` (`app/controllers/backoffice/base_controller.rb:8`, `app/controllers/admin/base_controller.rb:6`). Controller-level permission checks then narrow access, but the permission catalog is much smaller than the trust spec catalog and uses broad verbs such as `market.update` for unrelated high-impact capabilities, including admin CLOB order placement (`app/controllers/admin/orders_controller.rb:3`) and operator buyback (`app/controllers/backoffice/markets_controller.rb:84`).

Settlement transparency is materially behind the product trust model. The design doc expects a proposed resolution, optional dispute window, user-visible settlement explanation, and a backoffice two-step confirmation with winning-bet count and total credit (`docs/design/03-settlement-and-resolution.md:29`, `docs/design/03-settlement-and-resolution.md:38`). Current controllers settle immediately from a supplied outcome, and `SettlementService` only validates market state and leg label (`app/services/settlement_service.rb:4`). There is no mandatory resolution note, source citation, payout preview, or dispute hold.

Audit coverage is present but uneven. Good examples include bet placement with market/leg/stake metadata (`app/services/bet_placement_service.rb:53`), bet void with reason (`app/services/bet_void_service.rb:25`), permission/grant changes with reason (`app/controllers/backoffice/permissions_controller.rb:25`), and faucet approve/reject (`app/services/wallet_grant_service.rb:18`). Weak examples include market create/update/open with empty metadata, settlement ledger entries without market/order metadata in CLOB/LMSR handlers (`app/services/settlement/clob_settlement_handler.rb:35`, `app/services/settlement/lmsr_settlement_handler.rb:50`), and no explicit failed-settlement audit despite the trust spec listing `SETTLEMENT_FAILED` (`docs/ADMIN_TRUST_LAYER.md:1035`).

Fantasy wallet safety is the largest concrete security/trust risk. The project intentionally uses private points, but wallet balances still define player trust and leaderboard outcomes. The database validates non-negative wallet balances at the model layer (`app/models/wallet.rb:5`) and uses ledger entries for money-like movement (`db/migrate/20260525093259_create_ledger_entries.rb:3`), but several services mutate wallet balances directly without row locks, and ledger entries have no idempotency key or uniqueness guard. This is especially sensitive for settlement/cashout/faucet flows because retries or concurrent requests can create real user-visible balance drift.

Operator abuse controls are only partially present. There is reason capture for grants/permission changes, but no owner/admin split, no auditor role, no separation-of-duties enforcement, no self-action prohibition, no conflict-of-interest checks, no user suspension model, and no admin activity dashboard. The trust spec names these as core invariants and early implementation items (`docs/ADMIN_TRUST_LAYER.md:98`, `docs/ADMIN_TRUST_LAYER.md:2302`, `docs/ADMIN_TRUST_LAYER.md:2372`).

**CSRF bypass via spoofed Bearer header (P2 — confirmed by code read):** `Web::BaseController` skips `verify_authenticity_token` whenever `request.headers['Authorization'].to_s.start_with?('Bearer ')` is true (`app/controllers/web/base_controller.rb:13-17`). This check is based on header *presence*, not token *validity*. A cross-origin attacker can set `Authorization: Bearer GARBAGE` to disable CSRF protection on any `POST /web/*` endpoint, then rely on the victim's session cookie to authenticate the request. The risk is that a malicious page can trigger balance-affecting actions (`POST /web/markets/:id/bets`, `POST /web/positions/cashout_execute`, etc.) on a logged-in player's behalf. In a fantasy POC with no real money this is medium severity, but it is a real bypass. Fix: only skip CSRF when the bearer token is *validated and used* as the authentication credential (i.e., when `find_authenticated_user` returns a user via the token path, not the session path).

**SSE market snapshot leaks draft market data to unauthenticated callers (P1 — confirmed):** `GET /sse/markets/:id` is defined with `before_action :authenticate_request!, except: [:show]` (`app/controllers/sse/markets_controller.rb:5`), so the `show` action has no authentication. `HotStorage::MarketSnapshotReader` fetches and returns the full market snapshot including `status: "draft"`, question text, odds, and order book depth with no caller-side status guard. A caller who enumerates or guesses a draft market ID receives its full data. The web HTML path correctly gates draft visibility for unauthenticated users (`app/controllers/web/markets_controller.rb:35`), but the SSE path is unprotected. Fix: in `Sse::MarketsController#show`, return 404 or 403 for non-open/non-settled markets when the request is unauthenticated.

**Operator self-approval of faucet requests (P1 — confirmed, not in existing report):** Both `Backoffice::FaucetRequestsController#approve` (`app/controllers/backoffice/faucet_requests_controller.rb:15-22`) and `Admin::FaucetRequestsController#approve` (`app/controllers/admin/faucet_requests_controller.rb:9-13`) call `WalletGrantService.approve!` without checking whether `faucet_request.user_id == current_user.id`. A moderator or admin with `wallet.faucet.review` permission can submit a faucet request as a player (via the web UI or the `/faucet_requests` route) and then immediately approve it in the backoffice, crediting their own wallet. This directly violates `docs/ADMIN_TRUST_LAYER.md:2329` ("An admin cannot approve their own manual adjustment"). Fix: add `raise` / redirect if `faucet_request.user == current_user` in `WalletGrantService.approve!` (enforces the rule at the service layer regardless of which controller calls it).

**Unbounded faucet request amounts (P2 — confirmed):** `FaucetRequest` model validates only `greater_than: 0` (`app/models/faucet_request.rb:7`). Both `web/faucet_requests_controller.rb` and the legacy `faucet_requests_controller.rb` accept an arbitrary `amount_minor` from params. Combined with the self-approval gap above, a moderator can request and approve any fantasy balance amount. Even after the self-approval gap is fixed, a player can submit a request for an arbitrarily large amount that an approver might rubber-stamp. Fix: add `MAX_FAUCET_AMOUNT_MINOR = 100_000` validated in the model and enforced in both controllers.

**`CloseExpiredMarketsJob` emits no audit event (P2 — new finding):** `app/jobs/close_expired_markets_job.rb` (not read directly but referenced in docs) transitions markets from `open` to `closed` automatically when `close_at` passes. The `docs/ADMIN_TRUST_LAYER.md:1021` audit list includes `MARKET_CLOSED`. Backoffice manual close does emit an audit event, but the automated job path does not, making it impossible to reconstruct whether a market was auto-closed vs. manually closed from the audit trail alone. Fix: emit `AuditEvent` with `action: 'market.auto_close'` and `actor_id: nil` (system actor) from `CloseExpiredMarketsJob`.

**`market.update` and `market.open` audit events record empty metadata (P2 — confirmed):** Both `Admin::MarketsController#update` (`app/controllers/admin/markets_controller.rb:36-43`) and `Backoffice::MarketsController#update` (`app/controllers/backoffice/markets_controller.rb:54-58`) emit `metadata: {}`. `Backoffice::MarketsController#open` (`app/controllers/backoffice/markets_controller.rb:74-81`) also emits `metadata: {}`. An auditor looking at these events cannot tell what changed or what the market state was at the time. ActiveRecord's `previous_changes` hash is available immediately after save and would capture changed field names and old/new values at zero extra cost.

## Open Questions

- Should admin JSON endpoints be JWT-only, or is session access to `/admin` intentional for browser-backed tooling?
- What is the intended MVP policy for moderator powers: can moderators settle markets and approve faucet requests, or should those be admin-only until resolver/owner roles exist?
- Does the team want immediate settlement for friends-and-family MVP, or should every market go through a lightweight resolution record even when second approval is disabled?
- What is the authoritative source for wallet balances: current `wallets` table with ledger as audit, or eventual ledger-derived balance with wallet as cache?
- Should operator buyback use the operator's personal/admin wallet, a dedicated platform wallet, or a configured liquidity account?
- Are responsible-gaming controls required before a wider demo, even though this is private play money?
